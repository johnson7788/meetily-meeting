 会议记录后端存储架构

   数据库：SQLite（通过 aiosqlite 异步访问），文件位于 backend/meetily.db。

   数据表结构（6 张表）
   ┌────────────────┬───────────────────┬───────────────────────────────────────────────────────────────────────────────────────────┐
   │ 表名           │ 用途              │ 主要字段                                                                                  │
   ├────────────────┼───────────────────┼───────────────────────────────────────────────────────────────────────────────────────────┤
   │ meetings       │ 会议元数据        │ id, title, project_name, owner_user_id, created_at, updated_at                            │
   │ transcripts    │ 转录文本片段      │ meeting_id(FK), text, postprocessed_text, translated_text, timestamp, source, sequence_id │
   │ speaker_labels │ 说话人标签映射    │ (meeting_id, source) 联合主键, label                                                      │
   │ summaries      │ AI 生成的会议摘要 │ meeting_id(PK), status(pending/completed/failed), content, error                          │
   │ action_items   │ 提取的待办事项    │ meeting_id(FK), task, owner, due, done                                                    │
   │ templates      │ 摘要 prompt 模板  │ id, name, content                                                                         │
   └────────────────┴───────────────────┴───────────────────────────────────────────────────────────────────────────────────────────┘
   架构特点

   - 无 ORM，使用原生 SQL + Repository 模式
   - 所有子表通过 ON DELETE CASCADE 外键关联到 meetings
   - 无正式迁移框架，启动时通过 PRAGMA table_info + ALTER TABLE ADD COLUMN 动态补列
   - 数据路径可通过环境变量 MEETILY_DB_PATH 配置

   数据流（创建会议）
    1 POST /api/meetings → meeting_service.save_meeting()
    2   → repositories/meetings.py: create_meeting() (INSERT meetings)
    3   → repositories/meetings.py: save_transcripts() (INSERT OR REPLACE transcripts)
    4   → repositories/speaker_labels.py: upsert_default_speaker_labels()
   关键文件

   - backend/app/repositories/db.py — 建表 DDL
   - backend/app/repositories/meetings.py — 会议/转录/摘要 CRUD
   - backend/app/models.py — Pydantic 数据模型
   - backend/app/services/meeting_service.py — 业务逻辑层



   问题：每次访问会议详情页都会调用 LLM 重新生成章节，浪费 token。

   方案：将章节持久化到数据库，首次生成后缓存，后续直接读取。

   后端改动：

   1. db.py — 新增 chapters 表（id, meeting_id, title, summary, start_sequence_id, start_segment_id, start_timestamp, position）
   2. _common.py — 新增 row_to_chapter 辅助函数
   3. meetings.py (repository) — 新增 get_chapters() 和 save_chapters() 函数；get_meeting() 现在也返回 chapters 字段
   4. meeting_service.py — 重构为：
     - get_meeting_chapters() — GET 用，优先从缓存读取，无缓存时才生成
     - extract_chapters() — POST 用，强制重新生成
     - _generate_and_save_chapters() — 共享逻辑，生成后保存到数据库
   5. meetings.py (routes) — 新增 GET /{meeting_id}/chapters（读缓存），保留 POST /{meeting_id}/chapters（重新生成）

   前端改动：

   1. api.ts — extractChapters 改为 GET；新增 regenerateChapters 用 POST
   2. meeting-detail.tsx — 优先使用 meeting detail 返回的 chapters；新增"重新生成"功能
   3. ChapterNavigation.tsx — 新增 regenerating 和 onRegenerate props，显示"重新生成"按钮

   重启后端后，首次访问会生成并保存章节，之后访问直接从数据库读取，不再消耗 token。用户也可以手动点击"重新生成"强制刷新。
